Сложность: средняя. Примерно 2-4 недели на рабочий MVP для опытного macOS-разработчика.

Версия для стримеров: OBS source/plugin
Сделать источник для OBS или отдельное приложение, которое отдает “очищенный” экран. Для стримеров это самый практичный путь.
Сложность: средняя/выше средней, но продуктово проще, чем ломиться во все видеозвонки.

Захватывать экран без Telegram и отдавать как виртуальную камеру через Core Media I/O Camera Extension (Apple docs). Тогда Zoom/Meet увидят это как камеру.

Про “сделать как единственный основной монитор”: технически можно пытаться сделать виртуальный дисплей primary, но UX будет странный: менюбар, Dock, новые окна и курсор могут уехать на невидимый экран. Главные сложности:

Виртуальный дисплей: на macOS это не простой public API “создай монитор и пиши кадры”. Нормальный путь обычно через системное расширение/драйверный уровень. Apple описывает DriverKit/System Extensions как механизм для таких низкоуровневых расширений: DriverKit, System Extensions.
Permissions/install friction: пользователю придется дать Screen Recording permission, возможно approve system extension.
Latency: цепочка будет real screen -> ScreenCaptureKit -> наш render -> virtual display -> Zoom capture. Надо оптимизировать через Metal, иначе будет задержка/нагрузка.
Audio отдельно: видео можно сделать так; “скрыть звук Telegram из общего звука” потребует отдельного virtual audio device/mixer.

Да, прокторинг можно взять как жесткий тестовый стенд, но не как гарантию. Тут надо разделить два уровня.

Уровень 1: что видно в видеопотоке.
Если звонарка/OBS/браузер получает только выбранный SafeScreen-дисплей, то мы контролируем пиксели. Там можно добиться, чтобы не было Telegram, точек в Dock, уведомлений, второго окна браузера и т.д. Это хороший и достижимый benchmark: “в записанном шаринге нет лишних пикселей”.

Уровень 2: что локальная программа может узнать о системе.
Если это не просто звонарка, а прокторинг/корпоративный агент с доступами, он может видеть не только шаринг. Например:

Screen & System Audio Recording: может сам снимать реальный экран/звук, если пользователь дал доступ. Apple прямо описывает этот permission как доступ приложений/сайтов к записи экрана и аудио (Apple Support).
Accessibility: может узнавать/контролировать UI, активное приложение, фокус, элементы интерфейса; доступ выдается отдельно (Apple Support, AXIsProcessTrustedWithOptions).
Input Monitoring: может отслеживать ввод.
MDM/root/system extension: еще шире.
Вот против этого SafeScreen не защищает. Он защищает выбранный output, но не делает Mac “невидимым” для другой локальной программы с правами.

Поэтому правильная гарантия продукта звучит так:

Для обычных звонков и стриминга, где участники получают выбранный пользователем источник экрана, SafeScreen показывает только sanitized virtual display.

А вот так обещать нельзя:

Никакая локальная программа с расширенными правами не узнает, какие приложения запущены, куда ушел фокус, что реально происходит на основном мониторе.

Если “звонилка” честная, она шарит выбранный монитор. Если “звонилка” своя/агрессивная и ей дали Screen Recording/Accessibility, она теоретически может параллельно смотреть реальный экран или активное приложение. Да, если речь именно про браузерный прокторинг без нативного агента, то картина сильно лучше.

Браузерная страница сама по себе не может просто так прочитать список процессов, увидеть Telegram, залезть в другой экран или узнать, какие приложения открыты. Экран она получает через getDisplayMedia(), где браузер показывает системный picker, а пользователь выбирает источник. Спека W3C Screen Capture как раз построена вокруг выбора пользователем источника захвата: W3C Screen Capture. Сайт может получить видеопоток выбранного источника, но не “всё что захочет”.

Но есть важное “но”: браузерная страница может видеть собственное состояние:

страница потеряла фокус: window.blur / window.focus (MDN focus, MDN blur);
вкладка стала скрытой/неактивной: visibilitychange / document.visibilityState (MDN);
пользователь вышел из fullscreen;
изменился размер окна;
остановился screen share;
поток имеет странное разрешение/FPS/display surface.
То есть SafeScreen может скрыть визуальную смену фокуса внутри шаринга: например, в менюбаре не будет видно, что активен Telegram, Dock не покажет точку, окно не появится. Но если пользователь реально переключился с браузерной страницы на другое приложение, сама страница может получить blur. Это не пиксельный leak, это событие браузера.

Поэтому гарантия такая:

Скрыть ненужные окна из картинки: да.
Сделать браузерный screen share чистым: да.
Сделать так, чтобы браузерная страница не поняла, что она потеряла фокус, когда пользователь ушел в другое приложение: надежно нет.
Скрыть запущенные приложения от чисто браузерного сайта: обычно да, потому что у сайта нет API списка процессов.
Скрыть запущенные приложения от нативного прокторинга/агента: нет.
Аналог “Диспетчера задач” на Mac — Activity Monitor, по-русски обычно “Мониторинг системы”. Еще есть top, ps, htop в терминале.

Про режим “чтобы SafeScreen не было видно, и засейвленное приложение тоже не было видно”:
в Dock/⌘Tab наше приложение можно сделать почти невидимым как menu bar/background app. Это нормальный macOS-паттерн. Но в Activity Monitor легитимно спрятать процесс нельзя. Если Telegram/Chrome/наш SafeScreen запущены, системные инструменты должны их видеть. Скрывать процессы из Activity Monitor — это уже уровень root/kernel/private API и выглядит как malware-поведение, не как нормальный продукт.

Продуктово я бы формулировал так: SafeScreen защищает то, что попадает в выбранный видеопоток, а не переписывает реальное состояние Mac. Для браузерных звонков этого может быть достаточно: они видят только виртуальный монитор. Для прокторинга это можно использовать как тест на отсутствие визуальных ликов, но не как обещание обхода всех проверок фокуса/активности.
