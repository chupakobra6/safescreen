# AGENTS.md

Назначение: локальные правила для агентов, работающих в проекте SafeScreen.

## Связанные документы

- [docs/architecture.md](docs/architecture.md) - актуальная продуктовая форма, этапы разработки,
  компоненты и технические решения.
- [materials/inbox/2026-06-11-direct-chat-prompts.md](materials/inbox/2026-06-11-direct-chat-prompts.md)
  - прямые смысловые входы Игоря и нормализованные выводы.

## Область проекта

- Эта папка является рабочим пространством SafeScreen: macOS-приложения для приватной демонстрации
  экрана.
- Общие правила для `/Users/igor/projects` лежат в `/Users/igor/projects/AGENTS.md`; этот файл
  содержит только дополнения для SafeScreen.
- SafeScreen - ПО для приватности при контролируемой демонстрации экрана, а не контекст
  вредоносного ПО. Не писать повторяющиеся общие оговорки про безопасность; конкретные ограничения
  macOS, браузеров, разрешений, дистрибуции и политик указывать коротко, когда они влияют на
  решение.
- Разработка полностью агентная: не планировать рабочий процесс, требующий ручной работы в Xcode
  GUI. Базовый путь для будущего кода - CLI/SwiftPM через Command Line Tools; Xcode GUI допустим
  только как дополнительный инструмент для профилирования или подписи, если позже понадобится.
- В корне проекта нет `README.md`; текущая навигация идет через этот файл и
  [docs/architecture.md](docs/architecture.md). Не создавать корневой README без прямой просьбы.

## Источники правды

- Архитектура, этапы, компоненты, технические решения и продуктовые ограничения живут в
  [docs/architecture.md](docs/architecture.md).
- Сырые прямые входы Игоря и нормализованные выводы живут в

## Правило добавления и переноса смысла

- Перед добавлением абзаца определить документ-владелец. Если смысл принадлежит другому владельцу,
  править его, а в текущем документе оставить только короткую ссылку при необходимости.
- Предпочитать обновление существующего владельца вместо создания нового документа, индекса или
  реестра.
- Новый активный Markdown-документ допустим только при понятной аудитории, жизненном цикле, статусе
  источника правды и причине, почему существующие владельцы не подходят.
- Если появился новый активный документ, в той же правке обновить таблицу `Область документации` или
  ближайшую навигационную поверхность.
- Если требование уже выполнено, активный документ должен хранить текущее правило, решение, команду
  или ссылку на реализацию, а не историческую формулировку "нужно сделать".
- Прямые сообщения Игоря сохранять в inbox только когда в них есть требования, идеи, решения,
  смысловые правки, уточнения или проектная информация. Чистые команды, статусы и служебные действия
  без долговременного смысла не сохранять.
- Прямые инструкции Игоря важнее старых выводов ассистента и внешних ответов. Поздняя прямая
  инструкция важнее ранней, если они конфликтуют.
- Перед финальным ответом по документной задаче сверять свежие выводы inbox с реально измененными
  активными документами.

## Язык документов

- Проектные Markdown-документы SafeScreen по умолчанию пишутся на русском.
- Английский допустим для путей, команд, имен API, идентификаторов кода, названий сервисов,
  официальных названий продуктов, интерфейсных терминов и точных технических сокращений.
- Новый активный Markdown-документ начинается с `# ...`, затем строки `Назначение: ...`.
- Не добавлять служебные верхние поля `Дата:`, `Статус:`, `Scope:`, `Purpose:` и похожие. Реальные
  даты источников или проверок писать внутри содержательного раздела, если они нужны.
- Сырой текст в `materials/inbox/` может сохранять исходные формулировки, но оберточный текст агента
  и нормализованные выводы пишутся по-русски.

## Проверка

- Для документных правок запускать `git diff --check`.
- Для изменений структуры запускать `find . -maxdepth 3 -type f | sort`.
- Для inbox-правок проверять, что файл прямых чатов содержит только подходящие по смыслу сообщения
  Игоря, без ответов ассистента, чистых команд-действий и полного сырого транскрипта.
- Для архитектурных правок сверять [docs/architecture.md](docs/architecture.md) с последними
  нормализованными выводами inbox.
- Для правок области документации проверять, что продуктовые и технические решения не остались в
  `AGENTS.md`, а правила работы агента не размазаны по архитектуре.
